# web-seisaku-ai-team

LP制作・HP制作の受託案件を、Claude Codeのサブエージェントで「AIチーム」として回すためのリポジトリ。

## セットアップ

```bash
cd web-seisaku-ai-team
claude
```

`.claude/agents/` 配下は再帰的にスキャンされるため、`lp/` `hp/` のサブフォルダ構成のままで認識されます。
エージェントの識別は**ファイルパスではなく frontmatter の `name`** で行われるので、`name` は全体で一意にしてあります。

> **注意**: サブエージェントはセッション開始時に読み込まれます。ファイルを直接編集した場合、反映にはセッションの再起動が必要です。

## 構成

```
CLAUDE.md                 全セッション共通のルール（セキュリティ・品質・見積り原則）
.claude/agents/lp/        LP制作チーム（5役）
.claude/agents/hp/        HP制作チーム（5役）
.claude/skills/           職人技のスキル層（6種）
.claude/commands/         /lp-build /hp-build /proposal
docs/                     ヒアリングシート（LP用/HP用）・納品チェックリスト・料金の考え方
clients/_template/        新規案件の雛形
clients/<案件スラッグ>/    案件ごとの作業ディレクトリ
```

## AIチームの構成

### LPチーム — 1ページでCVを取る

| エージェント | 役割 | 特徴 |
|---|---|---|
| `lp-director` | 統括 | 各役へ委譲・統合・品質責任。要件が曖昧なら止まる |
| `lp-hearing` | 要件定義 | 要件を構造化し、**不足を質問リストとして返す** |
| `lp-copywriter` | コピー | デザインより先に「言葉で売れる状態」を作る。法務チェック込み |
| `lp-designer` | デザイン設計 | **コードは書かない。** 設計を先に固める |
| `lp-coder` | 実装 | 設計に忠実に実装。フォーム・DB・管理画面まで |
| `lp-qa` | 検品 | **修正しない。** 🔴🟡🟢 で指摘のみ返す |

### HPチーム — 複数ページ・情報設計・運用

| エージェント | 役割 | 特徴 |
|---|---|---|
| `hp-director` | 統括 | LPの作り方をHPに持ち込ませない |
| `hp-ia-planner` | 情報設計 | **成果物の8割を決める工程。** サイトマップ・導線・URL設計・CMS要否 |
| `hp-writer` | 原稿 | 「売る言葉」ではなく「信頼される言葉」。全ページのtitle/description |
| `hp-coder` | 実装 | 共通パーツの共有・SEO必須実装・リダイレクト |
| `hp-seo-qa` | 検品 | リダイレクト漏れ・noindex残りを最優先で潰す |

※ HPチームの要件定義は `lp-hearing`、デザイン設計は `lp-designer` を流用します（作法が共通のため）。

## スキル層 — 一流の職人技

`.claude/skills/` に技能を切り出し、各エージェントの `skills:` フロントマターでプリロードしています。
**技はスキル、手順はエージェント**という層分けです。

| スキル | 内容 | プリロード先 |
|---|---|---|
| `copy-craft` | 抽象語の潰し方、削り方、見出し、リズム | `lp-copywriter` `hp-writer` |
| `art-direction` | 配色・余白・階層・引き算・「AIが作った感」の回避 | `lp-designer` |
| `japanese-typography` | 行長・行間・約物・禁則・和欧混植・フォント軽量化 | designer / coder / qa 系 |
| `ux-writing` | ボタン文言、ラベル、エラー、空状態 | coder / qa 系 |
| `cro` | ファーストビュー、フォーム離脱、不安の除去 | copywriter / coder / qa / ia-planner |
| `photo-direction` | 素材の見極め、撮影指示書、権利、AI画像の扱い | `lp-hearing` `lp-designer` |

ディレクター2役にはスキルを積んでいません。**委譲が仕事なので、技を持たせると文脈を無駄に食う**ためです。

> **スキルを直すときは、スキルだけを直してください。** エージェント側に同じ内容を書き写すと、二重管理になって必ず食い違います。

## ヒアリングシート（LP用 / HP用）

**制作前にクライアントに聞くことは、LPとHPで違います。** 使い回すと事故ります。

| | LP用 | HP用 |
|---|---|---|
| 最重要 | **CVが1つに絞れているか** | **更新の主体**（CMS要否が決まる） |
| 次に重要 | **流入元**（広告/検索/SNSで作りが変わる） | **既存サイトのURL・ドメイン管理者** |
| 事故要因 | CVが複数 / 流入設計なし | ドメインを前の業者が管理 / 決裁者が別 |
| 素材の量 | 中 | **多**（原稿量がLPの数倍。最大の赤字要因） |
| 見積り前に確定 | 6項目 | 7項目 |

`docs/hearing-sheet-lp.md` / `docs/hearing-sheet-hp.md` はそのままクライアントに送れる形にしてあります。
各シートには「制作側の判断メモ」（相手に見せない、こちらの判断基準）と「危険信号」（この発言が出たら値上げか書面化）が入っています。

`lp-hearing` エージェントは `brief.md` の案件種別を見て、対応するシートを読んでから要件定義します。

## 使い方

```bash
# 1. 案件フォルダを作る
cp -r clients/_template clients/tanaka-seikotsu

# 2. brief.md に募集要項・ヒアリング内容を貼る

# 3. 実行
/lp-build tanaka-seikotsu
/hp-build tanaka-seikotsu

# 応募提案文を作る場合
/proposal （募集要項を貼る）
```

## 設計思想

**1. 分業して、文脈を汚さない**
サブエージェントは独立したコンテキストで動き、結果だけを親に返します。だから各エージェントに「全文を返すな、要点だけ返せ」と明記してあります。

**2. 設計を固める前に実装させない**
LPは `copy.md` → `design-plan.md` → 実装。HPは `sitemap.md` を最優先。作り直しが一番高くつくからです。

**3. 検品役は修正しない**
作った本人は自分のミスが見えません。指摘専任を分離し、🔴 が0件になるまでループさせます。

**4. 技と手順を分ける**
「配色をどう決めるか」は案件を跨いで変わらない**技**なのでスキルへ。「この案件で何を作り、どこへ出力するか」は**手順**なのでエージェントへ。だから `lp-designer` は薄く、`art-direction` は厚くなっています。

**5. AIが作った感を避ける**
`art-direction` スキルに、現在のAI生成デザインが収束しがちな3パターン（クリーム背景+セリフ+テラコッタ / 黒背景+アシッドグリーン / ブロードシート風）を名指しで禁止してあります。

**6. 儲けの構造をルールに埋め込む**
¥19,800の価格競争には参加しない、手数料20%を織り込む、修正回数の上限を握る、納品時に必ず保守提案する —— を `CLAUDE.md` と各エージェントに書いてあります。

## このリポジトリが解いていない問題

- **案件の獲得**はこのリポジトリの範囲外です。提案文は作れますが、応募するのは人間です
- **保守契約を取れないと、フロー型のまま頭打ちになります。** `delivery-checklist.md` の最後の項目を毎回サボらないこと
